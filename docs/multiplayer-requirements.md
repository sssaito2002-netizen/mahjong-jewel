# Jewel麻雀 対人対戦 要件定義（相談用ドラフト）

現状：Androidの完全オフライン対局は実装済み。この文書は対人モードの要件案であり、通信対戦はまだ実装していません。以下の「推奨」は確定事項ではありません。

## 確定した要件

- 離れた人同士が合言葉で同じプライベートルームに入る。
- 人間2〜4人で開始でき、空席はCPUが担当する。
- 初期版からAndroidとiPhoneが同じ部屋で対戦できる。
- 現行オフラインモードを維持する。

## 目的と範囲

友人同士が同じ宝石構成・ルールで4人麻雀を遊べるようにする。既存のオフライン1人対CPU3人は、ログインも通信も不要のまま残す。対人対戦に必要な通信だけを別モードとして追加する。

初期版はプライベートルームを推奨。自動マッチング、段位、ランキング、チャット、観戦、課金は後続の検討対象。

## 遊び方（確定事項あり）

| 候補 | 遊び方 | 必要なもの・制約 |
| --- | --- | --- |
| インターネットの合言葉ルーム（推奨） | 離れた場所から部屋番号で参加。Android/iPhone混在に対応 | 常時稼働する対戦サーバーと運用費。通信中はオフライン不可 |
| 同じWi-Fi内 | 同じネットワーク内で部屋に参加 | ホスト端末の離脱対策、ルーム探索、iOSローカルネットワーク権限。外部回線不要でもLAN通信は必要 |
| 1台を交代で操作 | 端末を回して各自の手番を操作 | CPU以外の応答時にも受け渡し。手牌を隠す確認画面が必要 |

ユーザー確認済み：最初に作るのは「離れた人と合言葉で同じ部屋に入る」インターネット対戦。LAN方式と1台交代は今回の範囲外。以降はこの方式の要件案。

## 参加から終局まで

1. 対戦を選択し、表示名を入力。初期版はアカウント登録なしを推奨。
2. 部屋作成で宝石牌とポッチ、対局ルールを設定。部屋番号／招待リンクを発行。
3. 参加者は空席に入る。全員がルールを確認して準備完了にする。
4. ホストが対局開始。席順と親をサーバーが抽選し、以降ルールを固定する。
5. 手牌・河・副露・点数・祝儀・接続状態を同期して対局する。
6. 和了時は全員に役・点数・祝儀内訳を表示。全員確認または確認待ち期限で続行。
7. 東風終了時に順位・祝儀収支を確定し、各端末に成績を保存する。

## ルームとルール

- 最大4席。人間2〜4人＋不足分CPUで開始する（ユーザー確認済み）。
- ホストだけが対局前に構成を編集できる。変更したら全員の準備完了を解除する。
- 現行の宝石カタログを共有。同じ宝石各1枚、同じ元牌2枚、ポッチ3種類まで、全136枚。
- 東風・25,000点、1本場1,500点（ロン1,500／ツモ各500）、東・西が場風牌。
- 55,000点コールド、0点未満トビ、トビ賞10枚。
- 順位チップ+50/+25/−25/−50と祝儀は別集計。
- 解放役は東風開始時に1つ抽選し全員に通知。途中で再抽選しない。
- 参加者全員のアプリとルールのバージョンが互換であること。開始後の宝石構成変更は禁止。

## 操作と同期

- 打牌、リーチ、チー、ポン、カン、ロン、ツモ、見送り、カーネリアン選択を送信する。
- サーバーを正とし、手牌・山・乱数・合法手・役・点数・祝儀・手番をサーバーで管理する。
- 各端末には自分の手牌と公開情報だけを送る。他家の手牌・未公開の山・裏表示は送らない。
- ロンと鳴きの応答は受付期限内に集めて現行ルールの優先順位で解決する。先着処理にしない。
- リーチ宣言時は全員に通知。オフラインと違い、オンラインは通知中もサーバーの期限を共通管理する。
- 各操作に対局ID・局ID・連番・一意の操作IDを付ける。再送されても打牌や支払いが二重にならない。
- 和了・流局・終局の確定イベントを保存し、再接続時に同じ点数と祝儀へ復帰する。

## 時間制限・離脱（数値は仮案）

- 打牌20秒、鳴き／ロン応答10秒、和了確認15秒を仮案とし、実機で調整する。
- 時間切れはツモ切り、鳴きは見送り。合法なロン／ツモは自動和了を推奨するが、採否を確認する。
- 切断から120秒は席を確保し、時間切れ操作はCPUが代行。復帰後は次の操作から人間に戻す。
- ホストが切断しても進行する。ルーム管理権を他の参加者へ移す。
- 永続離脱後はCPU継続を初期案とする。途中参加・他人による席の引継ぎは初期版対象外。
- 切断中・復帰中・CPU代行中は卓に明示し、二重接続は1席に1接続へ整理する。

## 成績とプライバシー

- オフライン成績と対人成績は区別する。CPU代行が入った対局も識別できるようにする。
- 同じ対局結果は対局IDで一度だけ保存。接続切れや再起動でも祝儀を重複加算しない。
- アカウントなしの場合は端末内保存。端末間同期・機種変更時の引継ぎは別途要件化する。
- 名前と部屋番号を公開検索しない。招待だけで参加できる方式を推奨。
- 推測されにくいルームコード、参加試行の回数制限、再接続用の秘密トークンを使う。
- 保管する対局ログの内容・保管期間・削除方法を運用開始前に決める。

## 受け入れ条件

- 実機4台が同じ局・点数・祝儀結果を表示し、各端末に他家の未公開情報が届かない。
- 応答が競合するロン／ポン／チー、ダブロン、槓、ポッチ、特殊祝儀を既存ルールと同じ結果で処理する。
- 再送・遅延・応答順の逆転・切断復帰でも不正操作や二重精算が発生しない。
- ホスト離脱後も残りの人が終局できる。サーバー再起動時の復旧方法も検証する。
- 東風終了時に4人の順位・祝儀収支が一致し、全祝儀収支の合計が0となる。
- 通信対戦機能の追加後も機内モードで従来のオフライン対局が動く。

## 次に決めたいこと

1. 対戦方式はインターネットの合言葉ルームで確定。
2. 人間2〜4人＋不足分CPU、Android/iPhone混在は確定。
3. iPhoneの配布経路。TestFlightならApple Developer登録と署名の準備が必要。
4. 持ち時間、切断猶予、時間切れ自動和了の可否。
5. ゲスト参加でよいか、名前と成績をアカウントで継続管理したいか。
6. サーバー運用の予算と、対戦ログの保管期間。

## 画面と通信方式の案

画面は「モード選択 → 名前入力 → 部屋作成／参加 → 待機室 → 対局 → 和了確認 → 結果」。待機室に合言葉、各席、CPU席、宝石構成、準備完了を表示する。参加時に満席・期限切れ・バージョン不一致を区別して案内する。

接続はHTTPS＋WebSocketを推奨し、サーバーで部屋と対局の状態を管理する。AndroidとiPhoneには同じルールエンジンを使い、見た目と入力だけを端末側で処理する。アプリがバックグラウンドに回った場合も切断復帰と同じ手順で状態を取り直す。iPhone側はWebViewの確認画面・音・保存・共有とセーフエリアも実機検証する。

## 実装順序の提案

ルールと成績を固定する → 2台＋CPUで部屋接続 → 4台の手番と鳴き同期 → 再接続・時間切れ → 祝儀精算の冪等性 → Android/iPhone混在の実機検証。
